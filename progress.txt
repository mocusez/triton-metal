## US-004' (2026-05-22) — Synthesis Phase C COMPLETED

### Implementation
Replaced the B2.3 stub (`notifyMatchFailure "deferred to Phase C (spt-fold)"`)
in `lowerRank1Reduce` with active α-fused inline emission for BLOCK > tpb.

**Strategy (per Architect Synthesis addendum):**
- Detect `spt = srcBlocked.getSizePerThread()[0]` from the rank-1 input.
- Compute `tpb = product(threadsPerWarp) * product(warpsPerCTA)` (already
  done earlier in the helper).
- Verify `BLOCK == tpb * spt` (propagate-coalesced-layouts pass invariant).
- Walk back to the producing `tt.load` via
  `op.getSrcs().front().getDefiningOp<tt::LoadOp>()`.
- Get the underlying memref via `findBaseMemref(loadOp.getPtr(), rewriter)`.
- Emit `spt` `metal.get_element` calls inline with
  `idx = tid * spt + spt_idx` (contiguous formula; E = BLOCK/(tpb*spt) = 1).
- Fold inline via `metal.BinaryExpOp(addOp/maxOp)` matching the existing
  combine dispatch.
- Continue into the existing B2.4 butterfly with the folded scalar as
  `inputScalarPT`. Tail handling is skipped (BLOCK == tpb*spt means no
  tail).

**Forward declaration:** `findBaseMemref` is defined later in the file
(near `LoadLowering` at :2248), so a forward decl was added immediately
before `lowerRank1Reduce`.

**Bail-out diagnostics** added for unexpected layouts:
- `spt == 1` when `BLOCK > tpb` (propagate pass didn't fire)
- `BLOCK != tpb * spt` (multi-iter tile loop not supported by Synthesis)
- Rank-1 reduce src not produced by `tt.load`
- Load is masked or missing `tt.addptr`
- Base memref walk-back failure

### Final IR shape (BLOCK=512, num_warps=8, spt=2)
```
%tid = metal.thread_id "x" : ui32
%tidI32 = cast %tid : ui32 -> i32
%c2 = arith.constant 2 : i32
%mul = arith.muli %tidI32, %c2
%c0_idx = arith.constant 0 : i32
%idx0_i32 = arith.addi %mul, %c0_idx
%idx0 = cast %idx0_i32 : i32 -> ui32
%e0 = metal.get_element %memref[%idx0]
%c1_idx = arith.constant 1 : i32
%idx1_i32 = arith.addi %mul, %c1_idx
%idx1 = cast %idx1_i32 : i32 -> ui32
%e1 = metal.get_element %memref[%idx1]
%acc = metal.binary_exp %e0, %e1, addOp : (f32, f32) -> f32
... (then standard B2.4 butterfly with %acc as inputScalarPT)
```

For BLOCK=1024 the same shape repeats with 4 `metal.get_element` + 3
inline `metal.binary_exp` folds before the butterfly.

### US-011 bench fix (subsequent session)
- Root cause of 0.02/0.04 GB/s: `_ELAPSED_TIME_FLOOR_MS = 0.1ms` in driver.py clamps
  single-call do_bench iterations; a 2-4KB kernel takes ~6-10µs GPU time so every
  sample hits the floor → reported time = 0.1ms always.
- Fix: batch N_CALLS_PER_ITER=2000 launches per do_bench lambda. Accumulated GPU time
  (~12-20ms) >> 0.1ms floor. Divide by 2000 to recover per-kernel time.
- Updated bench results (kernel-only GPU time via _PerfCounterEvent, 3 passed):
  - BLOCK=512:  6.00 µs/kernel  → 0.341 GB/s
  - BLOCK=1024: 6.41 µs/kernel  → 0.639 GB/s
- These are LATENCY-BOUND numbers, not DRAM-bandwidth numbers. The Metal backend
  supports rank-1 reduce only for BLOCK ≤ 1024 (BLOCK=2048 fails at tt.reduce
  lowering). A BLOCK=1024 kernel moves 4KB — entirely cache-resident — so the
  "GB/s" reflects dispatch overhead, not memory bandwidth. This is expected and
  correct; the bench now accurately measures kernel-only GPU latency.
- Multi-block kernel attempt (to reach bandwidth-bound regime) aborted: tt.store
  on pointer-arithmetic output hits an unimplemented lowering path; deferred to L2b.

### L3a-tileloop-2 — Rank-2 (axis=1 / chunked) reduce M*N >> tpb FIX (2026-06-21)

Goal: fix 2D (axis=1) `tt.reduce` for `M*N >> tpb`. The 8 cases in
test_metal_backend_reduce_{chunked,per_thread}.py + the i32/large
reduce_sum cases were xfail; the stale xfail reasons claimed "wrong runtime
semantics" but the real behavior was a **compile CRASH** in
TritonGPUPropagateCoalescedLayouts.

Two root causes:
1. CRASH: `rewriteReduceOperand` swapped a RANK-2 reduce's operand to the
   coalesced layout but never updated the reduce's `#ttg.slice` RESULT type
   → `verify_each` hard-abort. The documented rollback (snapshot `oldOperand`)
   was never actually implemented.
2. WRONG BODY: the old rank-2 body assumed `M*N == tpb` (one (row,col) per
   thread via the per-thread `adaptor` scalar). For `M*N > tpb` it (a) ran the
   FuncOpLowering tile loop with the INPUT's E (e.g. 512) while the output
   store needed E_out (8) → out-of-bounds store; (b) over-allocated TG memory
   (buf[M*chunk] = 36 KiB > 32 KiB limit); (c) reused the same scalar for
   every chunk.

Fix (full perf-optimal redesign, user-approved):
- `lib/Dialect/TritonGPU/Transforms/PropagateCoalescedLayouts.cpp`:
  `isSafeRewriteTarget` now gates to RANK-1 reduce operands only. Rank-2
  reduces are left untouched (the Metal rank-2 body reads its source tile
  directly from device memory, so it never needs the coalesced-operand
  rewrite). Crash gone.
- `TritonGPUToMetal.cpp` `findTileInfo`: new `reachesStoreNotThroughReduce`
  helper. When a func contains a `tt.reduce`, tensors that don't reach a
  `tt.store` without passing through the reduce (pre-reduce "fodder") are
  excluded from tile-loop sizing → the loop is now OUTPUT-driven (E_out) for
  reduce kernels, not input-driven. No-reduce funcs are byte-identical.
  (Bonus: rank-1 reduce kernels lose their redundant outer loop → leaner.)
- `TritonGPUToMetal.cpp` `ReduceLowering` rank-2 axis=1 body REWRITTEN
  (replaced the per-thread-owned + chunked branches, 471→271 lines):
  self-contained, mirrors lowerRank1Reduce. Walk back to the producing
  `tt.load` → base memref; allocate `rowBuf[M]` (M elements, ~4 KiB for
  M=1024, independent of N); each thread reduces a grid-strided set of WHOLE
  rows directly from device memory (`rowBuf[r] = sum_n device[base+r*N+n]`).
  Staging is HOISTED above the FuncOpLowering tile loop (runs once); the
  per-row result is read inside the loop via the OUTPUT per-iter index

  element→thread mapping). f32 column scan = single `scf.for` + f32 iter_arg

  storage (translator only threads f32 iter_args). M<=tpb (no loop) reads
  `rowBuf[tid mod M]`.
- `TritonGPUToMetal.cpp` `StoreLowering`: NEW sub-tpb bounds guard. When a
  stored tensor has fewer elements than tpb AND there is no tile loop, the
  device store is wrapped in `if (localTid < numElements)`. Without this an

strided reduce inputs are out of scope.

## Wall 17 — Rank-2 axis=1 reduce over a COMPUTED tile (Case C), Increment 1 (2026-06-24)

### Goal: make leet adder_transformer pass. Investigation (Explore agent) found
adder needs exactly ONE new backend feature — rank-2 axis=1 reduce over a
COMPUTED (non-tt.load) tile. Everything else in the kernel (tl.where/select,

is the whole remaining gap — but it spans 3 increments of difficulty.

### Increment 1 (SHIPPED): computed cone = device loads + f32 arith + unary math
New machinery in `TritonGPUToMetal.cpp` (before `struct ReduceLowering`):
  - `evalRank2ConeAt(v, rowBase, nVal, depth)` — re-derives one reduced element
    (row r, col n) as scalar Metal ops, recursing the PRE-conversion tensor cone
    to persistent leaves (device loads → device[rowBase+n]; tt.splat → scalar;
    dense-splat constant). Producers: tt.load, f32 {addf,subf,mulf,divf,
    maximumf,maxnumf} (BOTH operands recursed → two-tensor products like q·k
    work), unary math {exp,sqrt,log,sin,cos,erf,rsqrt}. Conversion-ordering-safe
    for the same reason as the rank-1 B2.3 walker: never consumes an intermediate
    op's converted scalar; rebuilds every node from leaves.
  - `findFirstLoadInCone` (representative load → per-program scalarOff) +
    `rank2ConeSupported` (upfront predicate → clean notifyMatchFailure, avoids
    relying on conversion rollback from inside the scf.for body builder).
  - `ReduceLowering` rank-2 branch: when src is not a direct unmasked tt.load,
    take the computed-cone path (f32 only): validate via `rank2ConeSupported`,
    find a representative load for `scalarOff`, then in the per-row column loop
    replace the single `emitColLoad(n)` device read with
    `evalRank2ConeAt(coneRoot, rowBase, n)`. Direct-load path unchanged.
